# TS-2610-001 · GraalVM native-image 下 JavaFX LCD 次像素文本合成退化

| 项 | 内容 |
| --- | --- |
| 编号 | TS-2610-001 |
| 日期 | 2026-10 |
| 状态 | 现象学根因已确证；**代码级根因尚未定位** |
| 影响面 | Windows x64 + GraalVM `native-image` + JavaFX 的 LCD 次像素文本渲染 |
| 复现工程 | 本仓库（最小复现，44 行有效代码） |
| 追踪入口 | 本仓库 issue #12 |

---

## 1. 现象

对同一段 JavaFX 代码（`Text` 元素设置 `FontSmoothingType.LCD`）：

* 以 `JVM Jar` 方式运行时，次像素合成结果正常：字形边缘存在灰度过渡与次像素色边，
  `R` / `G` / `B` 三通道覆盖量互不相等；
* 经 `native-image` 编译后运行时，结果异常：灰阶消失（观感为笔画偏细、发虚、无色边），
  三通道覆盖量**完全相等**。

## 2. 影响

* 原生镜像产物在 Windows 上的文本观感显著劣化，且**无任何异常抛出**（静默退化）；
* 影响范围为 LCD 次像素文本路径；灰度路径不受影响（见 4.3 节对照数据）；
* 在 C 级结论取得前，可用的**临时缓解措施见第 9 节**。

## 3. 结论分层（证据等级）

## 4. 观测数据

### 4.1 观测条件

| 项 | 取值 |
| --- | --- |
| 操作系统 | Windows 11 x64 |
| 显卡与缩放 | Intel UHD；显示缩放 1.5× |
| 判据样例 | 黑字白底，`Segoe UI` 14px（固定） |
| 快照缩放 | `Scale(1.5)` |
| 图形后端 | D3D（CI 无 GPU 时经 WARP，仍为 D3D 后端） |
| 对比方式 | 同一台机器、同一份源码、同一套运行参数，仅在 `JVM Jar` 与 `native-image` 两种构建之间对比 |

### 4.2 字形掩码：两构建逐字节相同（A 级）

| 字号 / 缩放 | 三通道掩码合计 | 单像素最大合计 | `R=G=B` 像素占比 |
| --- | --- | --- | --- |
| 12px / 1.0× | `27882 / 27880 / 27885` | 40475 | 37.1% |
| 14px / 1.0× | `35450 / 35448 / 35453` | 51010 | 41.6% |
| 21px / 1.0× | `76825 / 76823 / 76828` | 102576 | 49.0% |
| 14px / 1.5× | `76825 / 76823 / 76828` | 102576 | 49.0% |

⇒ 输入侧（DirectWrite 字形掩码）在两构建下**逐字节相同**，可排除「掩码生成差异」。

### 4.3 合成结果：两条判别特征（A 级）

| 观测项（黑字白底） | `JVM Jar` | `native-image` |
| --- | --- | --- |
| 三通道覆盖量 | `90666 / 91021 / 90713`（三值互不相等） | `126480 / 126480 / 126480`（**逐位相同**） |
| 逐列覆盖量（剖面） | `324 4629 2571 1670 1670 1561 1493 1549 2881 4215` | `0 6885 6885 3060 3060 2295 3060 3825 6885 6885 0` |
| 单像素覆盖之和（复杂字形处） | 不超过该像素三通道最大值之和 | `45855`，大于该像素三通道最大值之和 `40475` |
| 灰度路径对照 | 深核 1731 / 中间调 885 / 覆盖量 498320 / 色边 0 | 与 `JVM Jar` 逐项一致 |

由表中数据可提取两条判别特征：

1. **覆盖值二值化**：`native-image` 侧逐列覆盖量均为 `765 = 3 × 255` 的整数倍，即不存在中间取值；
2. **取样跨越相邻像素**：`native-image` 侧单像素覆盖之和**超出**该像素三通道最大值之和，
   而正确的按通道合成在数学上不可能超过该上限。

### 4.4 行为模型（B 级：推断）

综合 4.2、4.3 节：输入相同、输出不同，且输出具备上述两条判别特征，据此提出机制描述：

* 预期实现：`out_c = mix(bg_c, fg_c, m_c)`，即每个颜色通道使用各自的覆盖 `m_c`；
* 实际表现：`out_c = mix(bg, fg, s)`，即三通道共用同一个标量 `s`，且 `s` 呈二值化。

**该描述为对 A 级事实的机制化解释，尚未取得代码级证据支持，故标注为推断。**

## 5. 定位过程（收敛路径）

方法固定为：**提出假设 → 设计可产生定量结果的探针 → 以数据证伪或确认 → 更新结论**。

| 阶段 | 手段 | 观测结果 | 结论或排除项 |
| --- | --- | --- | --- |
| 1 | 输出三通道覆盖量 | `JVM Jar` 三值不等；`native-image` 三值相同 | 将观感问题转为可复现的定量判据 |
| 2 | 导出 DirectWrite 字形掩码 | 两构建逐字节相同 | 证伪「掩码生成不同」 |
| 3 | 离屏渲染并统计深核 / 中间调 / 覆盖量 / 色边 | 灰度路径一致；LCD 路径原生侧「中间调 = 0、色边 = 0、覆盖量偏高」 | 差异限定在 LCD 合成路径 |
| 4 | 分通道统计覆盖量 | 原生侧 `126480 / 126480 / 126480` | 通道信息被合并为单一标量 |
| 5 | 逐列输出掩码与合成覆盖量 | 逐列为 `3 × 255` 整数倍；单像素覆盖和超上限 | 得出两条判别特征，B 级模型成立 |
| 6 | 转储 `PrismSettings` 全字段；审计类初始化时机 | 44 字段全同；相关包全为 `RUN_TIME` | 排除「构建期固化运行期行为」 |
| 7 | 以 `-Ob` 重新构建并比对 | 体积变化，渲染数值逐位相同 | 排除编译优化等级影响 |
| 8 | 8 组版本组合矩阵 | 8/8 全部复现；`JVM Jar` 侧 8/8 全部 `collapsed=false` | 该缺陷不是回归 |
| 9 | 压缩为最小复现 | 本仓库（44 行有效代码 + 单一判据） | 结论可由第三方独立验证 |

## 6. 排除项

| # | 排除对象 | 依据 |
| --- | --- | --- |
| 1 | DirectWrite 字形掩码 | 两构建掩码逐字节相同（见 4.2） |
| 2 | 纹理上传 | 两构建调用同一 `prism_d3d.dll` 的原生例程 |
| 3 | 着色器 `.obj` 与 `*_Loader` 常量表 | `dstColor` / `glyphColor` / `gamma` / `maxTexCoordIndex` 等一致 |
| 4 | 几何类（见下）的几何与行距 | LCD 分支无特判；实测几何一致 |
| 5 | `_AlphaTest` 着色器变体 | 两构建均取 `false` |
| 6 | 构建期固化 | `PrismSettings` 44 字段全同 + 类初始化审计全 `RUN_TIME` |
| 7 | 运行环境差异 | 同一机器两进程，1.0× 掩码逐字节相同 |
| 8 | 编译优化等级 | `-Ob` 构建渲染数值逐位相同 |
| 9 | 六项运行期参数（见下） | 两构建一致 |
| 10 | 图形管线 / 驱动 | 同一后端与驱动；WARP 下同样复现 |
| 11 | Windows 应用清单 | 加清单前后行为不变 |
| 12 | 取样 / 抓屏探针本身 | 直方图核查后停用（该探针未捕获目标窗口） |

上表中两处“见下”的明细（逐项）：

排除项 4 —— 涉及的两个类：

* `MaskData`
* `GlyphCache`

排除项 9 —— 比对的六项运行期参数：

* `dpi=126.0`
* `outputScale=1.5`
* 字体族数 248
* LCD 对比度 1.2
* LCD 文本支持 `true`
* `subPixelMode=1`

## 7. 已限定的代码范围

代码级成因尚未确定，但范围已限定至下列调用链。命名取自 JavaFX **25.0.4** 的字节码核对结果。

1. **`com.sun.prism.impl.ps.BaseShaderGraphics#drawString(GlyphList, FontStrike, float, float, Color, int, int)`**
   —— LCD 分支；相关私有成员与调用包括 `lcdSampleInvalid`、`initLCDSampleRT()`、`drawLCDBuffer(float ×8)`，
   并把 `gamma` 常量传给着色器（`com.sun.prism.ps.Shader#setConstant(String, …)`）。
2. **`com.sun.prism.impl.ps.BaseShaderContext#validateLCDOp(BaseShaderGraphics, BaseTransform, Texture, Texture, boolean, Paint)`**
   —— 内部经 `getSpecialShader(…, SpecialShaderType)` 取用常量 **`TEXTURE_SECOND_LCD`**，
   其声明位置为 `com.sun.prism.impl.ps.BaseShaderContext` 的**嵌套枚举** `SpecialShaderType`，
   携带的名字为 `Solid_TextureSecondPassLCD`；该名字最终对应
   `com.sun.prism.shader.Solid_TextureSecondPassLCD_Loader` 与资源
   `com/sun/prism/d3d/hlsl/Solid_TextureSecondPassLCD.obj`。
3. **`com.sun.prism.impl.GlyphCache#addDataToQuad(…)`** —— 最终调用
   **`com.sun.prism.impl.VertexBuffer#addQuad(float ×12)`**（该 12 参数重载在 25.0.4 中唯一存在）。
4. **着色器资源** `com/sun/prism/d3d/hlsl/Solid_TextureSecondPassLCD.obj`（另有 `…_AlphaTest.obj` 变体）。
5. **`com.sun.prism.shader.Solid_TextureSecondPassLCD_Loader#loadShader(…)`** —— 常量表为
   `dstColor = 0`、`glyphColor = 1`、`gamma = 0`。
6. **`TEXTURE_SECOND_LCD` 分支的选择与参数装配路径**（即第 2 项所述路径）。

**未能继续限定的原因**：可核实的全部输入（掩码、几何、参数、常量表、着色器字节码、类初始化时机）
在两构建下均相同，且运行期无异常抛出；差异只能产生于 `native-image` 对该链路的编译或优化过程。
进一步定位需引入 GraalVM 侧的可观测性（分析调用树、生成代码比对），已超出黑盒实验可判定的范围。

## 8. 未决问题与后续工作

需区分的两种可能：

* **(A)** `native-image` 自身的编译/优化缺陷（例如与浮点或向量化相关的错误折叠、常量传播越界）；
* **(B)** JavaFX 与 AOT 编译的兼容性缺陷（例如依赖 JVM 运行期特性才成立的初始化或状态假设）。

建议的后续工作（以获取可核验产物为目标，而非继续黑盒试数）：

1. **最小隔离实验**：将第 7 节第 3 项的「三通道分别写入 + 多次偏移取样」逻辑抽成不依赖
   JavaFX 的最小样例，在 `native-image` 下检验是否同样出现三通道塌缩；若能复现，
   即可把范围收窄至具体语言构造或循环模式；
2. 以支持诊断输出的方式重编，对比该链路在两构建下的生成代码与对象布局；
3. 将隔离样例与本文数据提交上游（GraalVM 侧与 OpenJFX 侧各一份），由具备编译期可观测性的
   一方做最终判定。

## 9. 处置与规避

让原生构建的文本渲染走灰度路径（绕开 LCD 次像素合成）：

| 手段 | 设置方式 | 关键要求 |
| --- | --- | --- |
| 关闭 LCD 次像素合成、改走灰度路径 | 启动参数 `-Dprism.lcdtext=false`；或在代码最早期 `System.setProperty("prism.lcdtext", "false")` | **必须早于 `PrismFontFactory` 类加载**（该值只在静态初始化时读取一次），最迟应早于 `Platform.startup` |

## 10. 复现方法

1. 使用本仓库发布包：运行 `Dist/Update.cmd` 下载对应组合的包（JDK 23 及以上档的包内另含
   `build-report/lcd-repro-build-report.html`），随后分别双击 `Dist/RunNativeImage.cmd` 与
   `Dist/RunJVMJar.cmd`，比较两个窗口与控制台判据；
2. 从源码构建：见本仓库 `README.zh-CN.md`「快速开始 / 从源码构建」；
3. 判据：固定样例（黑字白底、`Segoe UI` 14px）下，一侧输出 `collapsed=false`、
   另一侧输出 `collapsed=true`，即判定为复现。

> 适用性说明：CI 构建机无 GPU（D3D 经 WARP），其数值足以判断缺陷是否复现；
> 渲染观感与像素级结论应以具备真实 GPU 与 ClearType 的机器为准。
